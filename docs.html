01文档说明#

1.1适用范围与读者

本页面向需要与 PowerMedia 智能媒体服务器进行系统集成或二次开发的技术人员，覆盖以下读者：

  • 集成方开发人员：需要调用上传、查询、播放授权、分享与任务类接口完成业务系统对接。
  • 实施与运维人员：需要了解鉴权模型、限流阈值、状态机流转、回调机制与异常处理约定。
  • 测试与验收人员：需要依据状态码、错误码与幂等语义设计用例并核对结果。

本页不覆盖产品功能说明与部署拓扑，相关内容见 产品能力、技术规格 与 内容保护。

2.3请求与响应通用结构

请求头通用项

通用请求头均可选，除标注外
请求头类型必填说明
Authorizationstring条件必填Bearer <JWT>；公开端点与分享匿名面除外
Content-Typestring条件必填有请求体时必填；上传用 multipart/form-data
Idempotency-Keystring可选写操作幂等键，见 2.5；格式 [A-Za-z0-9._:-]{8,128}
X-Request-Idstring可选调用方侧追踪标识；服务端会在响应中回填自身 request_id，用于对齐访问日志

错误响应信封　服务端存在两套并行的错误响应形态，接入方必须同时处理，不可只解析其一。

形态 A · 统一错误信封（播放协议面）code + message + request_id + retryable + details
{
  "code": "session_expired",
  "message": "session expired",
  "request_id": "…",
  "retryable": false,
  "details": null
}
形态 B · 简洁错误对象（业务管理面）error + 可选 reason
{
  "error": "share quota exceeded for this media (max 20 active shares)",
  "reason": "share_quota_exceeded"
}
  • 形态 A 用于播放协议相关端点，字段固定五项，details 无内容时为 null 而非缺省；响应强制携带 Cache-Control: private, no-store。
  • 形态 B 用于媒体库、上传、分享管理、管理端等业务路由，reason 为稳定的机器可读短码，error 为人读信息，两者均可能随版本演进。
  • 建议接入方按「先取 code，再取 reason，最后取 error/message」的顺序解析，避免形态差异导致漏判。

成功响应　不存在统一成功包装；响应体直接返回资源对象或结果对象。

  • 媒体列表 GET /api/v1/media 返回 {"items":[…]}。查询参数：library_id、file_type、q、sort（id_desc / created_desc / taken_desc，默认 id_desc）、limit（默认并上限 500；file_type=image 时上限 5000）、cursor（仅 sort=id_desc 时为上一条 id）。管理端未发布列表额外返回 has_more 与 next_cursor。
  • 统一任务列表使用不透明游标（Base64 的版本、排序、过滤摘要与快照），limit 默认 50、上限 200，并带回同一快照下的总数。
  • 分享列表使用 page 与 page_size，响应含 items、total、page、page_size。
  • 没有全站统一的 offset 参数，也没有 {"data":…,"success":true} 这类外壳。

请求级限额

请求护栏
限制项默认阈值超限行为
请求 URL 长度8 KiB鉴权前直接拒绝，不进入路由与请求体解析
JSON 请求体1 MiB拒绝；文件上传走 multipart，不受此项约束
每 IP 请求数1200 次 / 分钟拒绝，用于抑制单一来源请求洪泛
每 IP 并发256拒绝，避免突发请求占满处理槽

端点级限额（独立于上表）

  • 外部播放计划：每 IP 默认 30 次/分钟，超限 429、code=rate_limited、retryable=true，并带 Retry-After。并发会话默认 4/IP。密钥拉取失败默认 30 次/分钟后封锁 120 秒。详见 4.2。
  • 分享口令校验 POST /share/:token/verify：每 IP 默认 20 次/分钟（系统选项可调，钳制在 5–120），超限 429、reason=rate_limited、Retry-After: 60。
  • 其余业务端点没有另一套独立配额；它们只受本节请求护栏约束。

2.5幂等、重试与回调约定

幂等

Idempotency-Key 语义
项目约定
请求头Idempotency-Key
取值格式[A-Za-z0-9._:-]{8,128}，8–128 位
生效方法POST / PUT / PATCH / DELETE；GET 不参与
判定指纹SHA-256（方法 + "\n" + 路径 + "\n" + 请求体）
作用域「方法 + 路径 + 幂等键」三元组，同键不同路径互不影响
有效期默认 10 分钟，超时后自动遗忘
请求体上限1 MiB，超出直接拒绝
同键同体重放放行至业务处理，用于安全重试
同键异体409 idempotency_key_conflict，拒绝以防止重试时误用不同意图
键格式非法400 invalid_idempotency_key
请求体超限413 request_body_too_large
请求体不可读400 invalid_request_body

作用范围：幂等中间件挂载于 JIT 会话写操作与管理端生命周期触发接口（/admin/jit/lifecycle/run、/admin/jit/keys/lifecycle/run）。未挂载幂等中间件的写接口不保证重试安全，接入方须自行做前置查询或业务侧去重。各端点是否启用幂等，以 4.x 各节标注为准。

重试约定　客户端重试建议：仅对 retryable = true 或 5xx / 429 重试，采用指数退避并带上同一 Idempotency-Key。4xx（除 429）视为调用方错误，不应重试。服务端侧的重试策略见 6.x 各场景。

回调约定　服务端提供 Webhook 主动推送能力用于状态回传（事件清单、签名与重试见 6.5）；同时提供任务状态查询接口作为兜底（见 4.3）。二者可并用，建议以 Webhook 为主、查询为辅。

5.3错误处理与排查约定

  • 先分流、后判重试：解析出 code / reason 后，按 2.5 的重试约定分流；只有 retryable = true、429 与 5xx 参与重试。
  • 幂等保护：所有重试请求必须携带同一个 Idempotency-Key 与完全一致的请求体，否则会触发 idempotency_key_conflict。
  • 追踪对齐：错误响应中的 request_id 与服务端访问日志一一对应。反馈问题时必须附带该标识与调用时刻。
  • 缓存禁令：播放协议面错误响应强制 Cache-Control: private, no-store，接入方不得缓存。
  • 口令锁定：分享口令连续校验失败会触发锁定（code_locked），须由分享方通过解锁接口恢复。
  • 恢复：401 重新登录或换票；403 的授权码改授权或降级功能，不重试；202 segment_not_ready 等待 Retry-After 后取同一分片；429 服从 Retry-After；409 先查询当前资源再决定是否换幂等键。形态 A 用响应里的 request_id 对齐访问日志。没有值班联系人或处理时效；反馈使用第 8 节的公开联系方式，并附文档版本、章节与 request_id。
